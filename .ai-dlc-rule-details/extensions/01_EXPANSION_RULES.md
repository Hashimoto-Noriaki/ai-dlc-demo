# 拡張ルール (Extensions)

## 新 Bounded Context 追加手順

### 1. 既存との依存関係を先に設計する

```
プロンプト例:
「現在のコンテキストマップに [新コンテキスト名] を追加します。
既存コンテキスト一覧: [accounting, invoicing, ...]
どの既存コンテキストと依存関係を持つか、関係の種類 (ACL/OHS) とともに設計してください。」
```

### 2. ディレクトリスケルトン作成

```bash
# AI に依頼するコマンド
「app/contexts/[new_context]/ のスケルトンを
他のコンテキストと同じ構成で作成してください」
```

### 3. 既存コンテキストへの影響調査

AI にリポジトリ全体をスキャンさせ、影響範囲を特定する:

```
プロンプト:
「[new_context] を追加する際に既存コードへの影響がある箇所を
すべてリストアップしてください。特に:
- 共有している DB テーブル
- 同じモデルを参照している箇所
- API エンドポイントの変更が必要な箇所」
```

## 既存コンテキスト拡張ルール

### 後方互換性の維持

- API レスポンスのフィールドは**追加のみ許可**。削除・リネームは非推奨期間を設ける
- DB カラムの削除は2ステップ: ① Rails から参照削除 → ② カラム削除 (別 PR)
- 新しいバリデーションは段階的に適用 (既存データへの影響を確認)

### マイグレーション安全性チェックリスト

AI にマイグレーションを生成させた後、以下を必ず確認:

- [ ] `NOT NULL` カラム追加にはデフォルト値があるか
- [ ] インデックス追加は `algorithm: :concurrently` を使っているか
- [ ] カラム型変更はダウンタイムが発生しないか
- [ ] ロールバックが可能か (`reversible do` / `change` メソッド)

## API バージョン管理

```
変更の種類          バージョン対応
───────────────────────────────
フィールド追加      同一バージョンで可
フィールド削除      新バージョン + 非推奨期間 (3ヶ月)
レスポンス構造変更  新バージョン必須
認証方式変更        新バージョン必須
```

```
app/controllers/api/
  v1/    ← 既存 (維持)
  v2/    ← 新バージョン
```

## イベント連携の拡張

コンテキスト間を非同期イベントで連携する場合:

```ruby
# ドメインイベント定義
module Accounting
  module Events
    class JournalCreated
      attr_reader :journal_id, :amount, :occurred_at
      # ...
    end
  end
end

# 別コンテキストのサブスクライバー
module Reporting
  class JournalCreatedHandler
    def call(event)
      # ACL: 自コンテキストの言葉に変換してから使う
    end
  end
end
```

## リファクタリングルール

- リファクタリングは機能追加と同じ PR に混ぜない
- AI にリファクタリングを依頼するときは範囲を明示する
- `git bisect` で問題を追えるよう、小さいコミットを心がける
